优先级口径：第二审查材料 §0 纪律（行 10–29）与本轮已核实的本机事实优先；其余冲突标**待裁决**，不替负责人裁定。证据等级：实测=本轮观察；静态=配置/源码/快照；历史=历史验收记录（不代表本轮实测）。引用路径详见 `source-audit.md`、`capability-audit.md`、`bba-migration-map.md`。

## 1. Koishi 部署拓扑（待裁决）

- 01 §3 行 136–170 / README:17：无隔离补丁时，启用 Character 的账号每号独立 Koishi Runtime + 独立数据库。
- 第二审查材料 §3 行 114–118：暂定单逻辑 runtime 多 adapter，多 bot 隔离验证通过后才加账号，失败分 shard。
- 本地事实（快照静态）：Character 全部状态平面键 `group:<guildId>`/`private:<userId>` 无 selfId（`evidence/snapshots/chatluna-character/src/service/message.ts:149,163,173,178,198,225,250,258,266,280,311,317,369,397,407,445,695,840,938,1009,1013,1060`；`plugins/filter.ts:660`；`variable_store.ts:6-41`）；锁仅进程内；`_triggerSeq` 服务实例级共享。→ 单 runtime 多 bot 在 Character 启用前必须先补账号命名空间，两条路径成本都真实（01 行 147「二选一必须明确成本」）。
- 本机无 Koishi/ChatLuna 安装证据 → 安装版本 unknown；快照≠安装版本。
- 建议：两文档口径并存时按「先 2–4 号 + 隔离验证」执行，不预设每号一 runtime 为最终态；此为建议，非裁决。

## 2. ARTEX 许可与复用（口径差异，非冲突事实）

- 01 §4/§14（行 174–188、705）：优先复用测试过的基础设施（PostgreSQL 封装、鉴权、审计、SSE、模型配置/记录、恢复测试），并声明 AGPL-3.0 提醒。
- 第二审查材料 §0 行 27 / §9 行 349–351：ARTEX 是 AGPL-3.0 渗透测试产品，默认只借鉴领域无关接口，不作为运行时依赖；复制源码前先评估分发/网络义务。
- 本地证据：`evidence/ARTEX-meta.json` SPDX `AGPL-3.0`；`封存/BBA/app/LICENSE:10,63,636,660`；快照 `ARTEX-README.md:5,12`（Go+Next.js 渗透测试系统）。
- 裁决点：从封存树「借鉴接口/行为」与「复制源码」法律后果不同；本报告区分二者，不作法律结论。本地 Go 树整体继承 AGPL-3.0（bba-migration-map §AGPL）。

## 3. MVP 候选来源（待裁决；本地事实已部分改变前提）

- 01 §6/§12（行 260–285、589–610）：`group.acquire` 用关键词搜索 + 已验证 adapter，不足退 `group.discover`。
- 第二审查材料 §1（行 52–63）：MVP 候选第一阶段用用户提供的固定清单/导入数据；搜索接口需「确认存在具体接口、合法数据来源和授权」后才接入。
- 本地事实（capability-audit）：搜索接口真实存在且已安装启用（插件 `search-group`），来源=QQ 官方群搜索（静态）；授权=运营者本机配置（历史 spec-console §2 行 6 记录 36374700 关键字配置在跑——历史层级）。
- 事实限缩：插件无 cursor、无待审批状态查询 → 即便接搜索，`observe_join_request` 类状态查询仍缺（02 行 227 要求可验证才启用；DXC 历史用轮询通道+事件通道替代，`join-api.ts:115-165` + group-join 轮询，历史源码）。
- 裁决点：固定清单是保守建议非已裁决设计；搜索路径的前置条件（接口存在）已被本机事实满足一部分，「授权与状态查询」仍未满足。

## 4. 控制台内登录——设计包覆盖缺口（用户指定，单独列出）

- 产品事实（用户确认）：登录流程在控制台内完成，2026-10-14 拍板。成文旁证 `封存/DXC/docs/spec-console-v1.md:3-10`（老板口述首次成文；其「待审核」措辞不推翻用户决定）。
- 设计包主文本覆盖度：02 §1 行 10 仅「现有合格登录机制」；02 §6.1 行 309 仅 `accounts.login_state` 字段；03 §2 行 33 仅要求对照产品既有登录体验。**主文本三份设计均未规定「扫码登录在控制台内完成」的流程**——这是覆盖缺口，按 03 §2 行 33「不得默默取消已确认要求」。
- 历史实现证据（历史层级，非本轮实测）：`封存/BBA/docs/CURRENT.md` §3.12、README:5,27、`docs/CURRENT.md:139-145`——控制台后端经 loopback WebUI/OneBot 管理登录，5s 前端轮询 + 10s 服务端心跳 + 55min 凭证复用；二维码由浏览器本地渲染（`qq-login-dialog.tsx:413-427`）；刷新=显式用户动作且不重放（`login.go:9-13`）。
- 补设计建议（只定职责边界，不发明路由/API）：
  1. 控制台持有登录页状态机（等待扫码/已扫码确认中/已登录/需重扫/冷却），动作仅限用户显式触发的「刷新二维码/重新扫码/绑定/落库」；历史实现已有对应入口（`api.ts:897-947`、`server.go:1004-1009`，历史层级）。
  2. NapCat WebUI 作为控制面：每账号一实例绑定一 WebUI 端点；登录读操作（状态/二维码）与写操作（刷新）分离；在线判定不得只看单一信号（历史四条件口径：WebUI 登录 + core ready + QQInfo 在线 + OneBot self_id 一致，`CURRENT.md:138`）。
  3. 扫码成功后核验身份再绑定：`self_id` 与账号凭据一致才可入账（02 §1 行 15 禁止信任可声明 selfId；历史自动绑定口径 `CURRENT.md` §3.12）。
  4. 秘密边界：token/cookie/验证码不进模型上下文与日志，只存 secret_ref（01 §14 行 697）；`accessControlMode=none` 的本机 WebUI 配置（实测读回，值不含秘密）意味着登录面依赖 loopback 边界——QQ 安装实例配 `host="::"` 与「本机之外传输使用 TLS 或受控私网」（01 §14 行 698）之间需要负责人确认暴露面。
- 冲突/待裁决：spec-console 行 29 留了「WebUI 直接跨源 vs DXC 代理」二选一（审核时定）；用户已拍板流程本身，路径二选一仍未裁决。

## 5. 会改变架构的实施前事实（03 §2 完成条件要求先报告）

1. **插件 ID 阻塞**（静态确证，见 capability-audit §1）：历史硬编码 `dxc-join-api`，本机注册 ID 是 `napcat-plugin-cleaner` → 照搬历史 base 会 404。实施第一步需二选一（改部署名或改 base），且需一次实测确认。
2. **加群未决/超时语义冲突**：封存 BBA/DXC 把「24h 未批准→超时释放+冷却」当既定行为（`qq_group_join_runtime.go:335-346`，静态）；新设计 01 §5 行 252 要求 pending/unknown 不释放额度、审批超时只阻塞人工。迁移映射时不得默默采用任一方 → 待裁决。
3. **Character 合并 runtime 成本**（§1 证据）：不补账号命名空间就没有安全的单 runtime；门禁也拦不住 send.ts 直连路径（01 行 508 静态）。
4. **审计持久性**：guard ring 2000 重启即丢（`app/guard/guard.go:29,41,75`，静态）vs §1 第 10 条不得删除已验证审计 → 按 rewrite 处理（migration-map）。
5. **许可 unknown**：group-analysis 快照许可 NOASSERTION（package.json 未快照）；复制其代码前必须补证（第二审查 §0 行 27 纪律）。
6. **无安装基线**：Koishi/ChatLuna 本机无安装证据；本地 9B 权重无证据 → registry 保持 unknown，不得承诺吞吐（01 行 60–61 静态）。
7. **运行面观察**（实测，2026-10-23）：6099/6002/3001 无监听；6199 napcatd 在监听；8166（Swift IQ3_S 服务）在监听。历史验收均不构成本轮实测（03 §7 行 157）。
