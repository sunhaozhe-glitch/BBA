## 阶段 A 前置：任务自动收口与持续 worker

专项静态审查并经 Astra 抽查确认：`observations.go:772–798` 写入 result、履约 slot、设置 subtask 成功和 execution 已观察，但该路径未终结父 task；当前生产 Go 实现的 task 更新点未发现自动达标归并。先写最小回归证明或推翻这一缺口，再补父任务归并器，不要仅凭数据库约束存在就认为会自动结项。

明确达标、候选耗尽、截止、取消及 pending/unknown 未决时的父任务状态；在事务中更新状态/版本、事件与所需 outbox。验收必须从可信 observation 进入，断言父 task 最终状态，而不只断言 result 数。取消后迟到事实不得复活父任务。

`p0-20-execute/engine.go:808–839` 有意限制受控单次执行和 attempt=1；HTTP server 本身未启动长期工作循环。保留单次受控入口，另实现可恢复的确定性 worker，串起分页展开、claim、Reserve、受控派发、观测消费、对账、期限处理和仅在证据许可时重试。不得通过循环调用单次 CLI 或对 unknown 自动重发来伪装长期调度。覆盖进程重启、多 worker 争抢、旧 owner、重复事件、迟到审批和暂停后的不再派发。为持续聊天目标另定义周期、预算与结束条件，不能用一次加群成功表示整个运营目标完成。

1. 核实并固定后端、每账号 Character Runtime、单群 collector、共享模型服务、NapCat 实例的启动和配置关系。依赖版本锁定；开发构建产物由当前用户可写，不盲目递归 chmod/chown。

4. 对账必须具备持久请求、worker消费、可信成员读取、结果归并、终态/失败收据，明确 pending/unknown 不等于未发送，无法判断时不重发。

## 阶段 B：群分析 P1a → P1b → P1c

建立真实业务链：可信入站事件 → 白名单与账号/群身份校验 → 单群 collector 去重 → 持久消息窗口 → L0 统计 → 必要时模型摘要 → Summary.v1 校验及保存 → UI 可查看。

要求：
- 同群被多个受管账号观察时不重复采集/计费；明确定义 collector owner、事件唯一键与交接规则。
- 消息持久存储能按授权窗口解析 message_refs；统计与摘要保留输入窗口、来源、版本、生成时间、过期时间和 limitations。
- Summary.v1 的结构验证之外，还验证消息引用归属、窗口、账号、过期、producer来源；不要编造 40 位 commit 满足 schema。若发布包无法证明 commit，形成合约调整决策并同步生成类型/测试。
- 原文 local_only 不得流向外部模型；外部允许的输入必须按政策脱敏。保留期与删除传播覆盖摘要/图引用。
- 区分确定性统计、模型推断与群成员自述，不把推断存为已验证事实。
- 定时分析只选一个调度所有者。由 Task Engine 负责时关闭插件重复 cron。
- P1c 先做控制台可读报告；群内自动发送报告是独立动作，仍走发送门禁。

验收：乱序/重复/重启不重复归并；跨群跨账号引用拒绝；空窗口、过期、模型超时和非法输出有显式状态；先用合成事件端到端，再在有效授权范围下采集真实窗口并产出可校验 Summary。真实输入不可得时明确标记阻塞，继续其他开发，不用模拟摘要冒充真实产出。

## 阶段 C：分析驱动的 Character 对话

复用现有 ChatLuna/Character，不另造聊天大脑。设计稳定 GroupContext 接口：群/账号范围、最新有效摘要引用、近期话题、活动窗口、当前发言人、冷却/配额、当前任务允许的参与目标、来源及过期时间。

将 GroupContext 受控注入 Character 的实际 prompt/上下文路径；只传相关摘要和必要片段，不把整张图和全部历史塞给每条回复。群消息内容没有任务管理权限。

链路：入站 → L0 触发/白名单/发言人/冷却 → 有效群上下文 → Character/L1 → 文本校验 → 现有 permit 与 adapter 门禁 → 发送回执/unknown。

要求：同群多机器人不互相接话；重启不回放过期回复；一个账号的人设与记忆不串另一个账号；摘要陈旧时退回已定义的局部上下文策略。按需加载上下文，普通聊天不必调用 ARTEX Planner。

验收至少比较两组有不同群上下文的合成输入，证明实际 Character 路径使用正确摘要，而不仅是测试函数拼接字符串。覆盖越权提示、身份隔离、发送失败unknown/no-resend和人设持久化。

## 阶段 D：ARTEX 双图与目标推进

用户明确需要双图，本阶段是本轮必要交付，不再无限延后到“将来 P2”。但保持设计激活条件：真实 Summary 与受控只读 ARTEX 接线未满足时，可实现/测试适配器，禁止宣称真实双图链已通过。

先查实际 ARTEX 仓库、版本、图模型、MCP/API 和许可证，决定用现有服务接口还是可独立复用模块；端口 :8082 是设计线索，不是当前可用事实。不要照搬渗透测试 scheduler，也不要新增平行 Planner/执行器。

实现并成文：
1. 事实图：保存 Summary 原件引用、账号/群/时间窗口、证据来源和版本；模型摘要以带来源的模型产物记录，不能把模型结论升级为确定事实。更正追加新版本/失效关系，任务推断不能改写来源。
2. 任务图：目标、子目标、依赖、适用范围、预算、截止时间、成功条件、状态及证据引用。首个模板限定为“受控入群 → 确认成员 → 观察 → 形成摘要 → 建议参与 → 受控聊天 → 观察结果”。
3. anchor：对照实际 ARTEX 定义建立 QQ 领域绑定；至少明确 workspace、task、account/group scope、事实/摘要版本与图节点之间的稳定关联，不把 anchor 变成另一个可漂移的任务真相。
4. `task_graph_roots` 映射及必要迁移。PostgreSQL 仍是执行与结果真相；图提案经 schema、范围、版本、预算、批准及现有最后发送门执行。
5. 提案状态：生成、校验、待批准/批准、应用、过期/冲突/拒绝；具体枚举与现有合约统一。审批不是发送，生成不是应用。
6. 结果回流：可信观察/ResultReducer更新任务图投影；幂等关联执行ID与图节点，图更新失败可恢复，不能为修图重复 QQ 动作。
7. 有界重规划：只有新证据、阻塞或预定观察点触发；限制次数/费用/时间，不扩大账号、群、动作权限；缺证据进入等待或建议。

验收：重复摘要不重复建事实；同任务版本重复提案不重复应用；旧图提案在任务版本变化后拒绝；图不可用不旁路执行；结果回流失败重放不重发；取消后晚到成员观察只更新事实和审计；重启恢复后 anchor 与任务根对应不丢失。交付单个目标跨两次观察周期的完整证据链，证明双图实际改变了下一步提案而不是只画图。

## 阶段 E：Web UI 逐步整合

前端沿用阶段 A 的同一应用。页面和后端契约同步交付，至少覆盖：
- 总览：目标进度、在线账号、待审批/未知结果、模型/collector/runtime故障。
- 账号：控制台内扫码登录、实例绑定与登录状态、身份核验、配额、冷却、权重、暂停。登录状态/二维码读取与显式刷新分开；token/cookie不出现在浏览器日志或模型上下文。优先后端代理并说明技术决策。
- 任务：创建/范围/预算、批准、暂停/恢复/取消、对账；confirmed/pending/unknown分别展示。
- 群：统计、摘要、来源片段、时间窗口、分析状态、参与策略。
- 人设：按账号配置、预设版本、对话策略、当前发言人和冷却。
- 模型：实际provider/model标识、路由、可用性、并发、超时、费用；普通聊天过载不自动升级付费模型。
- 双图：事实/任务切换、anchor与来源跳转、提案差异与版本冲突；先只读可追溯，再增加批准操作，不先造通用DAG编辑器。
- 审计与运行：执行/回执/未知、日志脱敏、备份恢复状态、配置与健康检查。

UI 中刷新页面不得重放写动作；按钮禁用需有原因，异步失败保留真实错误；状态必须来自 API，不用 mock 值伪装接通。先做列表/详情可用闭环，再打磨视觉。使用浏览器实际验证登录状态显示、任务控制、失联、409冲突、unknown、刷新恢复和窄屏。
