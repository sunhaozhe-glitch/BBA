    Connect to local API

    Fixture session

    This is an offline fixture session. There is no QR-code login, no device authorization and no external session refresh in this build. Connecting only keeps the operator bearer token in memory for this tab and issues explicit local API requests; nothing here signs in to QQ, calls a real model provider or refreshes an external session.

    The token must already exist as a SHA-256 digest in the local resolver file supplied with -resolver-file; this page cannot create or reissue one. Token stays in memory for this tab and is never persisted. Mutations stay locked until development operation mode is explicitly enabled after connecting.

    Disabled

    Reads are always available after connecting. Create, control, reconcile and proposal actions are locked until this mode is enabled. The server must be started with -development-operations to expose the create, control and proposal routes; otherwise the resulting 404, 403 or 409 remains visible in the error log.

    Group analysis report

    No task selected

    Reference data only. Each proposal row below shows the provenance recorded when the proposal was generated: which live Summary id and version, which graph anchor, which evidence kinds, the source manifest digest and the selection rule the generator actually consulted. This record is not a decision, it grants no approve or apply authority, and a statistical Summary is not verified group semantic understanding. Proposal state, execution, result, claim and permit in the BBA ledger remain execution truth. Offline fixture only: no live QQ, model-provider or external graph connection is used.

    GroupContext report

    No context loaded

    Read-only operator view of the same durable GroupContext the Character runtime consumes. Account and group are explicit; no runtime credential is used, no message is sent, and no permit or execution is created.

    Only accounts returned by GET /v1/accounts are listed. The server re-checks the account workspace and scope.

    Select an account and enter a group ID, then load the read-only GroupContext report.

    Source, Summary version, generated/expiry timestamps, active window, speaker lease, daily remaining and topics are shown exactly as the GroupContext response reports them. A Summary is reference data, not verified semantic truth, and it never authorises a send.

    Task graph and analysis readback

    Reads GET /v1/tasks/{task_id}/graph. This is the same durable graph projection the task detail uses: graph revision/scope, anchors and any summary or analysis fields the backend reports. It does not call ARTEX, a model or GroupContext directly, and an analysis state is reported, never inferred into execution authority.

    Select a task to read its graph projection.

    Plan, materialize, and work trace

    Orchestration mode not reported

    Legacy apply stays intent-only: it records an applied intent and never emits work. Materialize turns a latest approved proposal into the S1 execution plan, work items, and applications; it is a separate, explicit action below. Work and application rows are the execution readback.

    Orchestration mode

    Changing the mode does not run anything by itself. The server re-reads the authorization revision and any in-flight proposal that depends on a changed basis is invalidated rather than retried.

    Materialize an approved proposal

    The server materializes the exact approved proposal named above. The approval reference and proposal digest must match the durable approved row; a mismatch is rejected. Materialize is separate from legacy apply, which remains intent-only.
